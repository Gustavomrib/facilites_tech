# Deployment, Rollback, and Backup

Three workflows added on top of the existing CI (`backend-ci.yml`,
`e2e-pr.yml`, `staging-smoke.yml` — see `docs/CI_CD.md`):

| Workflow | Trigger | Does |
|---|---|---|
| `.github/workflows/deploy.yml` | push tag `v*.*.*`, or manual | Builds the backend Docker image, pushes it to GHCR tagged with the commit SHA, then (if configured) deploys it over SSH |
| `.github/workflows/rollback.yml` | manual, with an `image_tag` input | Redeploys a previously-built image tag — no rebuild, no schema rollback |
| `.github/workflows/backup.yml` | daily cron, or manual | `pg_dump`s production and uploads the result as a build artifact |

**Honesty check on what's actually been verified**: the deploy/rollback
workflows have never run against a real host — there is no production
server target in this repo, and inventing one wasn't appropriate. What *is*
verified: the Docker image builds correctly (`backend/Dockerfile`, already
production-shaped — multi-stage, non-root, healthcheck), and the backup +
**restore** path was tested for real against the local Postgres instance
used for this session's E2E runs — see §3.

## 1. Deploy

`deploy.yml` always builds and pushes the image to
`ghcr.io/<owner>/<repo>-backend`, tagged with the commit SHA (immutable —
this is the tag rollback.yml redeploys) and `latest`. The SSH-deploy half
only runs if `DEPLOY_HOST` is set; otherwise the job logs a warning and
stops there, so this workflow is safe to have merged before a target host
exists.

### Required secrets (GitHub Environment `production`)

| Secret | Purpose |
|---|---|
| `DEPLOY_HOST` | SSH host of the production server |
| `DEPLOY_USER` | SSH user |
| `DEPLOY_SSH_KEY` | Private key for that user |
| `DEPLOY_PATH` | Directory on the host containing `backend/docker-compose.yml`, `backend/.env`, and this repo's `scripts/` (specifically `remote-deploy.sh` and `wait-for-http.sh`) |

### What happens on the host

`scripts/remote-deploy.sh <image>`:
1. `docker compose pull api` — pulls the exact tag, no rebuild on the host.
2. `docker compose up -d api` — restarts it. The container's own start
   command (`docker-compose.yml`: `sh -c "npx prisma migrate deploy && node
   dist/main.js"`) applies any new migrations before serving traffic.
3. Polls `GET /api/health/ready` (`scripts/wait-for-http.sh`) until it
   passes or times out. A failed health check exits non-zero — the workflow
   run goes red, which is the "bad deploy" signal (see §2).

`docker-compose.yml`'s `api` service now has both `image:` (used by this
flow) and `build:` (unchanged — `docker compose up --build` for local dev
still works exactly as before).

## 2. Rollback

`rollback.yml` takes an `image_tag` input (a commit SHA from a previous
`deploy.yml` run's summary, or any tag already pushed to GHCR) and runs the
exact same `remote-deploy.sh` script with that tag. This is a **code**
rollback only:

- Prisma migrations here are forward-only (no `down` migration files are
  generated by `prisma migrate deploy`). Rolling back the code does **not**
  undo a schema change a bad deploy might have applied.
- Before rolling back, check whether the bad deploy's migration is backward
  compatible with the previous code (additive changes — new nullable
  column, new table — almost always are; a dropped/renamed column is not).
  If it isn't, a code-only rollback will crash on the old code path
  expecting a column that no longer exists — restoring from a backup taken
  just before that deploy (§3) is the real fix in that case, not this
  workflow.

**Signals a deploy is bad** (act on these): `deploy.yml`'s health check
step failing; `/health/ready` failing after the workflow reports success
(caught it in the gap between the check and real traffic); a spike in 5xx
in the app's structured logs; a spike in 401s specifically on
`/auth/refresh` (points at a cookie/CORS/secret mismatch from a config
change, not the code itself).

**After a rollback**: confirm `/health/ready` is green, confirm the GHCR tag
now running matches what you intended (`docker compose ps api` on the host,
or the rollback workflow's summary), and do one real login + session-reload
by hand — the automated smoke suite (`staging-smoke.yml`) is the fast way to
confirm this instead of doing it by hand every time.

## 3. Backup and restore

`backup.yml` runs `scripts/backup-postgres.sh` against
`secrets.PRODUCTION_DATABASE_URL` daily and uploads the gzip dump as a
30-day GitHub Actions artifact.

**Known constraint**: this requires the production Postgres to be reachable
*from GitHub's hosted runners* — fine for a managed Postgres with a public
(or IP-allowlisted) endpoint, not fine for a database firewalled to only the
app's own network. If that's the case here, run the same script on a cron
**on the DB host itself** instead:
```
0 6 * * * DATABASE_URL=postgresql://... /path/to/scripts/backup-postgres.sh /var/backups/mnb
```
Either way, **GitHub Actions artifacts are not real off-site backup
storage** — 30-day retention on the platform that also hosts your CI is a
safety net for "I need yesterday's data back", not a disaster-recovery
plan. Once a cloud provider is chosen, extend `backup-postgres.sh`'s output
step to also push to S3/GCS/etc.

### Restore procedure (tested for real this session, not just written down)

```bash
gunzip -c meu-negocio-no-bolso-<timestamp>.sql.gz | psql "$DATABASE_URL" --set ON_ERROR_STOP=1
```

This was actually run end-to-end against the local Postgres used for this
session's backend/E2E work: `pg_dump` → gzip → restore into a scratch
database (`mnb_restore_test`) → row counts compared table-by-table against
the source. Every table matched exactly (`companies`: 75/75, `users`:
71/71, `products`: 4/4, `sales`: 11/11, `customers`: 5/5, `accounts`: 5/5).
The scratch database was dropped afterward. This confirms the dump format
and restore command are correct — it does not substitute for periodically
re-running this drill against production-scale data and the real deploy
target once one exists.

Worth flagging precisely because it was a real, silent-until-run bug: the
first version of `backup-postgres.sh` passed `DATABASE_URL` straight through
to `pg_dump`, which rejected it outright — Prisma's `?schema=public` query
parameter isn't something `pg_dump`/`psql` understand, it's Prisma-specific.
The script now strips it before calling `pg_dump` (see the script's
comment). This was only caught by actually running the backup against a
real database, not by reading the code.

## 4. Env vars touched by this change

| Variable | Where | Purpose |
|---|---|---|
| `IMAGE` | `backend/docker-compose.yml`, `scripts/remote-deploy.sh` | Which pre-built tag `docker compose up` runs (defaults to a local build tag for dev) |
| `DEPLOY_HOST` / `DEPLOY_USER` / `DEPLOY_SSH_KEY` / `DEPLOY_PATH` | GitHub Environment `production` secrets | SSH target for `deploy.yml` / `rollback.yml` |
| `PRODUCTION_DATABASE_URL` | GitHub Environment `production` secret | Source DB for `backup.yml` |
